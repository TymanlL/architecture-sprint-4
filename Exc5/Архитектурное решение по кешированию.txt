 Архитектурное решение по кешированию

 Мотивация

 Текущие проблемы
1. Медленная загрузка страницы для операторов
2. Длительный расчет стоимости заказов (до 30 минут)
3. Высокая нагрузка на MES при отображении списка заказов

 Цели кеширования
1. Ускорение загрузки интерфейса MES
2. Оптимизация расчетов стоимости часто заказываемых моделей
3. Снижение нагрузки на базу данных MES

 Элементы для кеширования
1. Список активных заказов для MES
2. Результаты расчетов стоимости популярных моделей
3. Статусы заказов

 Предлагаемое решение

 Типы кеширования
1. Серверное кеширование
   - Cache-Aside для списка заказов
   - Write-Through для статусов заказов
   - Refresh-Ahead для предварительных расчетов стоимости

2. Клиентское кеширование
   - Browser Cache для статических ресурсов MES UI
   - Session Storage для пользовательских настроек

 Обоснование выбора паттернов

1. Cache-Aside для списка заказов
   - Преимущества:
     - Гибкое управление кешем
     - Простота реализации
     - Хорошо работает с read-heavy нагрузкой
   - Почему не другие:
     - Write-Through избыточен для редко меняющихся данных
     - Read-Through усложнит логику без значительных преимуществ

2. Write-Through для статусов
   - Преимущества:
     - Гарантированная консистентность данных
     - Подходит для частых обновлений
   - Почему не другие:
     - Cache-Aside может привести к рассинхронизации
     - Write-Behind рискован для критичных данных

 Sequence Diagram для чтения списка заказов:
@startuml
actor Operator
participant "MES UI" as UI
participant "MES API" as API
participant Cache
participant "MES DB" as DB

Operator -> UI: Запрос списка заказов
UI -> API: GET /orders
API -> Cache: Check Cache

alt Cache Hit
    Cache --> API: Return cached data
else Cache Miss
    API -> DB: Query orders
    DB --> API: Return orders
    API -> Cache: Update cache
end

API --> UI: Return orders
UI --> Operator: Display orders
@enduml


 Sequence Diagram для обновления статуса:
@startuml
actor Operator
participant "MES UI" as UI
participant "MES API" as API
participant Cache
participant "MES DB" as DB
participant RabbitMQ as Queue

Operator -> UI: Изменение статуса
UI -> API: PUT /orders/{id}/status
API -> DB: Update status
API -> Cache: Update cache
API -> Queue: Send status update
API --> UI: Success response
UI --> Operator: Display confirmation
@enduml

 Стратегия инвалидации кеша

||Стратегия||Применимость||Преимущества||Недостатки|
||TTL (Time-based)||Список заказов||- Простота реализации<br>- Предсказуемая нагрузка||- Возможна работа с устаревшими данными|
||Event-based||Статусы заказов||- Мгновенная инвалидация<br>- Консистентность данных||- Сложность реализации<br>- Доп. нагрузка на сеть|
||LRU (Least Recently Used)||Расчеты стоимости||- Эффективное использование памяти<br>- Автоматическая очистка||- Возможна потеря актуальных данных|

 Выбранная стратегия:
1. Для списка заказов:
   - TTL (5 минут) + Event-based при изменениях
   - Обоснование: баланс между актуальностью и производительностью

2. Для статусов заказов:
   - Event-based
   - Обоснование: критичность актуальности данных

3. Для расчетов стоимости:
   - LRU + TTL (24 часа)
   - Обоснование: оптимизация памяти и актуальность цен

 Технологическое решение

1. Redis как основное хранилище кеша:
   - Поддержка различных структур данных
   - Встроенная поддержка TTL
   - Атомарные операции
   - Высокая производительность

2. Конфигурация:
   - Размер кеша: 10GB
   - Максимальное время хранения: 24 часа
   - Политика вытеснения: LRU
   - Репликация: Master-Replica

 Дополнительные соображения

1. Безопасность:
   - Шифрование данных в кеше
   - Аутентификация для доступа к Redis
   - Network isolation

2. Мониторинг:
   - Hit/Miss ratio
   - Cache size
   - Eviction rate
   - Response time

3. Отказоустойчивость:
   - Redis кластер
   - Graceful degradation при отказе кеша
   - Автоматическое восстановление
